# 0003 · 时之笛在 iPhone 17e（8 GB）上的优化：调研

## 1. 设备与既有实测

| 项 | 值 | 来源 |
|---|---|---|
| 机型 | iPhone 17e（`iPhone18,5`），8 GB，iOS 27.2.1 | `devicectl` |
| 系统给进程的上限 | 8 GB 机型约 **4.8–5.0 GB** footprint（外部实证） | 0002 `research.md` §2.2 |
| 2026-11-17 会话结局 | **4 次 jetsam**：00:53（1.04 GB）/ 01:03（3.96 GB，`vm-pageshortage`）/ 07:49（3.48 GB）/ 08:07（3.86 GB，`fc-thrashing`） | 设备 `systemCrashLogs` 的 `JetsamEvent` |
| footprint 峰值 | **3.78 GB**（compressed 0.78） | `[mem] guest file` 的 `peak so far` |
| 读放大 | **21.29 GB** 读入 / 7.6 GB 文件（≈2.8×），**112 万** 次 page-in | 同上 |
| 首次启动 PSO 归档 | **7.6 GB**（34,649 对，54 个 `.mtl4a`） | prebuild 日志 |

结论：被杀的机制有两层——一是 **footprint 逼近上限**（jetsam 只认 dirty/compressed/wired），二是 **文件缓存抖动**（`fc-thrashing`：归档与 RomFS 的页把 guest 自己的文件页挤出去，再读回来）。

## 2. 上游同期已有的 OoT/iPhone 事实（同一作者的实测记录，非本机）

上游 `dm/games/0400486024DEC000/README.md`（Memory 节）与 PR #2270 / #2566 / #2681：

- **iPhone 17（同为 8 GB 级）**：一次提交后驻留集峰值 **3,431 / 3,345 MB**；wired 最高 **5,163 / 4,939 MB**；一次会话在这次数接近上限时被 jetsam 结束（village → castle grounds 载入，单帧载入 **301 个纹理 / 204 MB**）。
- **Mac 上的构成**（同一份代码）：走进村庄 footprint **6.36 GB**，其中 **4.4 GB 是 Metal 内存**，而 **2.9 GB 是 304 MB 渲染目标池里的 target**——绝大多数已 20 秒以上未用，只是纹理对象还活着。修掉之后同一路线 **5.35–5.47 → 3.70–3.80 GB**。
- **时之笛的常驻大头**：12288×12288 Depth16 阴影目标 **296 MB**，长期住在一个 **333 MB** 的堆里；village 里"活着的渲染目标"稳定约 **2.1 GB**（动态分辨率把场景目标缩了，但 target 仍按满尺寸占位，NVN 的布局允许它在同一块内存里叠，Metal 不允许）。
- **共享纹理（ghost）表**：只按条数（`NGHOST=512`）封顶。

## 4. 差距：还剩什么可以做（按确定性排序）

| 手段 | 针对 | 预期 | 风险 | 本轮 |
|---|---|---|---|---|
| 上游 5 个修复 | 堆余量、零缓冲、staging | 实测 30–100 MB，且是已合入的代码 | 低 | **已取** |
| 小内存机型默认档（源预算 / staging 空闲 / 归档 1 GB / 视图 16 路） | staging 与源缓冲无上限、归档吃文件缓存 | 100–300 MB | 低（都是上游 opt-in，只是换默认） | **已做** |
| ghost 表按字节封顶（384 MB） | 512 条共享纹理在 OoT 上可达近 1 GB | 200–600 MB | 中低（复用既有淘汰路径，只改判据） | **已做** |
| 纹理镜像全局预算 + LRU（Ryujinx 式） | host 侧全部纹理 | 300–700 MB | 高：要动 package 生命周期 | 下一轮 |
| 小内存机型降内部分辨率 + MetalFX 上采样 | 2.1 GB 常驻渲染目标 | 最大（按比例） | 高：新特性，上游 PR #2270 未合并 | 下一轮（评估 #2270） |

**明确不做**：把 guest 放回匿名内存（9 GB pool 直接进 footprint）、关闭 Frame buffering（省不到 10 MB）、靠降分辨率换内存而不做上采样（画面代价与收益不成比例，且用户已选择 30 fps + Handheld）。

## 5. 结论

1. 这一轮的目标不是"重构渲染层"，而是**先把已证实的三类浪费收掉**：堆余量、零缓冲、以及"空闲却仍占 GPU 内存"的共享纹理。
2. ghost 表的字节封顶是唯一能在**不引入新机制**的前提下给出确定性上限的一项：淘汰路径（延迟释放 + 引用计数 + 空闲判定）上游已在用，本轮只把判据从"条数"扩展到"字节"。
3. 所有新默认都只在**小内存机型**（启动时 room < 8 GB）生效，Mac 行为完全不变，可用 `DM_*` 逐个覆盖，便于同一台手机上做对照。
4. 最终判定必须在真机上：Mac 没有 jetsam，数字不能代表手机（0002 已确立）。
